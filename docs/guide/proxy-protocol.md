# PROXY Protocol

[English](./proxy-protocol.en.md)

PROXY Protocol 用于在多级转发链路中传递用户的真实来源 IP，使后端服务能够识别客户端的实际地址，而不是中间节点的地址。

普通转发时，后端看到的是入口机或出口机的 IP。开启并正确配置 PROXY Protocol 后，真实 IP 信息会随数据流一起传递，后端即可获取客户端的原始地址。

---

## 工作原理

PROXY Protocol 通过在 TCP 连接建立后、业务数据发送前，插入一行包含来源 IP/端口和目标 IP/端口的头部信息来传递真实 IP。接收方解析该头部后，可将其中的地址用作客户端真实地址。UDP 没有「连接开始」，ForwardX 隧道在每个 UDP 数据报开头各写一个 v2 头，见下文 [UDP](#udp)。

典型链路示意：

```text
用户 -> 中转（入口）-> 落地（出口）-> 后端服务
```

在这条链路中：

- 中转（入口）负责**发送** PROXY Protocol 头，将用户真实 IP 告知下一跳。
- 落地（出口）负责**接收**该头，并可选择继续向后端**发送**。
- 后端服务需要支持 PROXY Protocol，才能正确读取真实 IP。

---

## 配置项说明

PROXY Protocol 在端口转发、隧道或转发链的高级设置中配置，规则引用这些资源后会继承对应的配置。

| 配置项 | 含义 |
| --- | --- |
| accept proxy（接收） | 接收上一跳传来的真实 IP 信息 |
| send proxy（发送） | 将真实 IP 信息发送给下一跳 |

**入口发送和出口接收应成对开启。**

- 只开启入口发送时，PROXY 头会被当作普通数据继续传递，下游无法解析。
- 只开启出口接收时，出口会等待一个并不存在的头，导致连接挂起或失败。

## SNI 分流

端口转发资源和主机型转发组的 SNI 分流规则可以单独设置 PROXY Protocol，适合落地服务需要取得客户端真实 IP 的场景：

| 开关 | 作用范围 | 行为 |
| --- | --- | --- |
| 发送 PROXY | 单条规则 | 分流器连接落地后先写入 v1 或 v2 头，再回放客户端 ClientHello |
| 接收 PROXY | 入口主机 + 入口端口 | 分流器读取 ClientHello 之前先解析上游的头，v1 和 v2 自动识别 |

- 接收开关属于入口端口：保存任一条规则时，面板会把它同步到同一入口端口的全部 SNI 规则；新加入该端口的规则沿用当前值。
- 开启接收后，没有头或头格式错误的连接直接断开；解析出的客户端地址用于最大连接数和来源 IP 限制，也写入发给落地的头。
- 头的字节不计入限速和流量。
- 转发链和隧道的 SNI 规则不能开启：转发链入口连接的是下一跳，隧道出口只看到本机地址，都拿不到客户端地址。
- SNI 填 `*` 的默认去向规则同样可以发送 PROXY 头，详见 [SNI 分流](./sni-routing.md)。
- 需要入口 Agent `3.10.0` 或更高版本；版本不足时面板拒绝开启。

## GOST 隧道推荐配置

### 上游已携带 PROXY Protocol 头

适用于上游本身已通过 PROXY Protocol 传入真实 IP 的场景：

1. 开启**入口接收上游**，读取上游提供的真实 IP。
2. 开启**入口发送到出口** + **出口接收入口**，让真实 IP 穿越隧道。
3. 若后端支持 PROXY Protocol，开启**出口发送到目标**。

### 上游为普通 TCP 连接

适用于用户直接连接入口，上游不携带 PROXY Protocol 头的场景：

1. **入口接收上游保持关闭**，由入口连接地址自动生成真实 IP 信息。
2. 开启**入口发送到出口** + **出口接收入口**。
3. 若后端支持 PROXY Protocol，开启**出口发送到目标**。

## UDP

只有 ForwardX 隧道支持 UDP 的 PROXY Protocol，并且只能使用 v2（v1 没有 UDP 格式）。在隧道的 PROXY 设置中打开「同时用于 UDP（仅 V2）」后：

- **每个数据报都带头**：UDP 没有连接开始。如果只在会话首包加头，首包一旦丢失，整段会话都没有来源信息；因此每个数据报开头各有一个 v2 头（IPv4 为 28 字节、地址族 0x12，IPv6 为 52 字节、0x22），后端需要按数据报解析。
- 入口接收上游：每个数据报都必须带合法的 UDP v2 头，否则丢弃；头被剥去后再转发。
- 入口发送到出口 + 出口发送到目标：由入口在加密前把头加在数据报前面，目标收到「头 + 原数据」。回程数据不带头。
- 头的字节不计入限速和流量。出口发给目标的每个数据报比原来多 28 或 52 字节，接近路径 MTU 的业务可能因此出现 IP 分片。
- 需要所有入口 Agent `3.10.0` 或更高版本。

其他转发方式无法为 UDP 写入头，面板会禁用开关：

| 转发方式 | 原因 |
| --- | --- |
| iptables／nftables | 内核转发，不改写数据报内容 |
| realm | PROXY 只实现在 TCP 路径 |
| GOST | 会把头作为单独的一个数据报发出，接收端无法识别 |
| socat、Nginx | 不支持 UDP 的 PROXY Protocol |

## 兼容性说明

| 维度 | 说明 |
| --- | --- |
| 协议支持 | TCP 支持 v1 和 v2；UDP 仅 ForwardX 隧道支持，且只能用 v2 |
| 后端要求 | 后端服务必须显式支持 PROXY Protocol（如 Nginx `proxy_protocol on`、HAProxy 等） |
| 面板限制 | 不支持的转发方式或场景下，面板会自动禁用相关开关 |
| 多级链路 | 每一跳是否开启接收/发送，需根据实际链路路径单独配置 |

## 常见误区

- **只在入口开启 send proxy 不够**：后端收不到真实 IP，除非出口也配置了 accept 并向后端继续发送。
- **后端不支持时不要开启 send proxy to target**：后端会将 PROXY 头当作业务数据处理，导致连接异常或协议解析错误。
- **UDP 只在 ForwardX 隧道上生效**：其他转发方式的 UDP 无法通过 PROXY Protocol 传递真实 IP；ForwardX 隧道开启后，后端必须按数据报解析 v2 头。
- **多级链路需逐跳配置**：中间每一个节点都需要根据其在链路中的位置，分别配置接收和发送，不能只配置首尾两端。
